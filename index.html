How well do AI models handle real C, C++, ROS and Linux engineering?

CROS scores coding models on short but genuinely hard software engineering tasks — the kind a robotics engineer finishes in under two hours: C and C++ work, ROS1 and ROS2 packages, Linux services and build chains, tests, debugging, and the messy parts of old, long-lived codebases. Two tracks: execution measures the delivered work, how long it took and what it cost; planning & analysis measures how well a model understands an unfamiliar codebase and reasons about a plan before any code is written.

How the score is built

What each number on this track means.

Points
Each metric carries a fixed number of points and a report earns some of them. —
Normalized value
Points earned ÷ points available × 100, so every metric reads on the same 0–100 scale.
Planning score
The raw points added up, 0 to 100. It is a weighted total, not an average of the normalized values.
Grading
Every claim in a report is checked against the actual code before points are given. A confident claim that turns out to be invented costs hallucination points; a real defect the report never mentions costs efficacy points.

Method

How the benchmark works

What the tasks look like

Every task is drawn from real development work and is meant to take a competent engineer under two hours. The suite covers C and C++, ROS1 and ROS2 packages, robotics integration, Linux services, toolchains and deployment, writing and fixing tests, debugging existing code, and old codebases that have outlived their original authors — with the ordinary workflow around all of it: builds, dependencies, and repository conventions.

Track 1 — Execution

The model does the task. Three measures:

  • CROS Execution score — the quality of the delivered work, 0 to 100. Higher is better.
  • Time index — how long the model took, normalized. Lower is better.
  • Cost index — what the run cost, normalized. Lower is better.

Time and cost are relative indices, not seconds or dollars. They are useful for comparing models with each other, not for predicting a bill.

Track 2 — Planning & codebase analysis

The model reads an unfamiliar codebase and reviews an implementation plan against it, in read-only mode, without writing any code. Its report is then checked claim by claim against the actual sources and graded on six metrics:

    Each metric is shown normalized to 100 (points earned ÷ points available). The CROS Planning score is the raw points added up, 0 to 100.

    The planning task so far

    A read-only architecture review of a 90-step, 4,360-line implementation plan for a new raid encounter in a long-lived C++ MMO: a Windows client, four Linux server services, SQL migrations, CI gates and content tooling. The prompt asked for non-feasible or blocking steps, architectural errors, pattern violations, breaking changes and unplanned technical debt, delivered as an evaluation table, an analysis table, a mitigation plan and corrective actions. Around sixty of the reports' claims were verified against the code before grading.

    Effort settings

    Models are run at the reasoning effort listed beside them. A different effort setting moves every number, so the label is part of the result — the same model at a lower effort is a different row, not the same one.

    Where this stands

    These are early results: one execution task and one planning task, five models, one run each. Treat them as a first signal, not a settled ranking. As tasks are added the scores will move, and this page updates with them.

    Reproducing and contributing

    The results shown here live in assets/data.js in the repository — one list per track, one entry per model. Corrections and additional runs are welcome through the GitHub repo.
